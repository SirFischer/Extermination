# Changelog

## October 15, 2026
### Added
- Darkness pass with a player light and drifting fog, replacing the no-op post-effect shader.
  - **Dim quad.** `Game::Render` now draws a screen-space `sf::RectangleShape` sized to `mWindow->GetSize()` at `(0, 0)` with `sf::Color(0, 0, 0, 166)` (~65% black) after `World::Render` and before `mf::GUI::Render`. `World::Render` already ends with `pWindow->ResetView(true)` before drawing the inventory, so the world pass and the UI pass are separated by a view reset and the quad slots into that seam: everything drawn before it is dimmed, everything after it (GUI, next-wave button, statistics) stays bright. The quad is deliberately screen-space — a camera-space quad would track the camera and be affected by zoom.
  - **Player light.** New `Emissive` helper (`src/States/Game/World/Lighting/Emissive.hpp`/`.cpp`) generates a 256x256 RGBA radial gradient once at load (`Init()`, idempotent via a `static bool`, called from `World`'s constructor) and draws it with `sf::BlendAdd` through the `sf::RenderStates` overload of `Window::Draw`. The gradient is premultiplied (`rgb = alpha = 255 * a`) with `kGradientInner = 0.0`, `kGradientFalloff = 2.2` and `kGradientPeak = 0.45`. The peak matters: `BlendAdd` *adds* to the framebuffer, so a gradient whose centre reaches full white adds 255 to every channel and blows the scene out to a hard white disc. Capping the peak at 0.45 and letting the falloff start at the centre keeps the core a soft glow instead of a blown-out blob. `DrawLight` uses a `static sf::Sprite` scratch object (no per-frame allocation, no per-frame texture construction) and early-returns when the gradient is not ready, when the window is null, when the diameter is non-positive, or when the tint is fully transparent — degrading to "no light" rather than a white square over the screen. `ResourceManager` has no API to register a raw texture, so `Emissive` owns the gradient itself. The player light is drawn at `mPlayer->GetPosition() + sf::Vector2f(19.f, 27.f)` (half of the player's `SetSize(38, 54)`, since `GetPosition()` is the entity origin, not its centre) with a 180px diameter and a warm `sf::Color(255, 214, 150)` tint. The diameter is deliberately close to the player's own size — a much larger radius washes the whole screen and reads as a permanent overlay rather than a light the player carries.
  - **Fog.** `Fog` was an orphaned stub (`GenerateFog()` declared but never defined, `Render()` a no-op, `Update(double)` moving sprites 1px/s, referenced nowhere). It is now implemented: two layers of seamlessly tiling 2D value noise generated on the CPU at load time (three octaves, lattice coordinates wrapped modulo the period so the texture tiles, deterministic hash-based gradients so no asset file is needed), uploaded to `sf::Texture` with `setRepeated(true)` and `setSmooth(true)`. The layers follow the `Background` parallax idiom — sprite scaled to fill the view, `setTextureRect` driven by camera position times a move factor — plus a time term for a slow rightward drift, at different speeds (6 and 14 px/s) and opacities (0.30 and 0.22) for depth. `Fog::Update` takes `(float pDeltaTime, const sf::View &pCameraView)` and is called with `mCamera.GetView()`. Unlike `Background`, which is drawn *before* `SetView(mCamera.GetView())` and therefore lives in screen space, the fog is drawn *after* it and lives in camera space — so each sprite is repositioned to `camPos - viewSize / 2` every frame to stay centred on the view, and the texture rect supplies the parallax. `Fog::Update` takes `float` to match every other `Update` in the codebase, the incorrect "separate thread" header comment is gone, and `GenerateFog()` is defined rather than declared-and-undefined. Fog is drawn with the default `sf::BlendAlpha` at render step 9: it is atmosphere, not light, so it is dimmed by the quad along with the rest of the world.
  - **Render order.** `World::Render` now draws fog after `ParticleManager::Render`, then the player light, then the muzzle flash, then `ResetView(true)` and the inventory. Fog comes before the emissives (fog is atmosphere and must be dimmed); the emissives come before the dim quad (that is the whole point — they survive at reduced intensity with correct occlusion). `World::Update` runs `mFog.Update(pDeltaTime)` and `MuzzleFlashManager::Update(pDeltaTime)` immediately after the background update loop, so fog parallax uses the current camera position exactly like the background loop above it.
  - **Muzzle flash** (implemented in parallel by the Gameplay agent): `MuzzleFlashManager::AddFlash`/`Update`/`Render` are called from `Weapon.cpp` and `World.cpp` respectively, and the flash is drawn as an emissive at render step 11 so it lights the scene through the darkness.
### Removed
- Deleted `assets/shaders/post-effects.frag` and the `mPostEffectShader` member/load in `Game`. The shader was a pass-through that only forced `color.a = 1.0` — it did nothing, and shipping a no-op shader is dead code. `Game::Render` now calls the no-argument `Window::Display()`.

## October 15, 2026
### Changed
- Build system: bumped the C++ standard from `c++17` to `c++26` in `Makefiles/default_vars.mk` (`CFLAGS := -Wall -Werror -Wextra -std=c++26`), matching the project's "use the latest C++ standard" policy. `c++26` is the latest standard the installed toolchain supports — `g++ (GCC) 16.2.1` reports `__cplusplus == 202400` for `-std=c++26` (and its alias `-std=c++2c`). The whole project rebuilds cleanly with `-Wall -Werror -Wextra` at the new standard (zero warnings, so no new deprecations or stricter-rule failures), and the game still launches. The `Yuna` submodule and `Yuna/mfGUI` still pin `c++17`; that is not a problem for linking (see below).
- CI: upgraded the GitHub Actions toolchain so the `-std=c++26` build actually works there. `.github/workflows/makefile.yml` now pins `runs-on: ubuntu-24.04` (instead of the floating `ubuntu-latest`) and installs `gcc-15`/`g++-15` from the `ubuntu-toolchain-r/test` PPA, because the runner's stock GCC 13 cannot compile `-std=c++26` (GCC 15+ is required). The Makefiles hard-assign `CC := g++` (immediate assignment), so `CC`/`CXX` environment variables are ignored and `g++` is resolved from `PATH`; the workflow therefore repoints the `gcc`/`g++`/`cc`/`c++` alternatives at the GCC 15 binaries via `update-alternatives`, which fixes both the main build and the `Yuna` submodule build in one step. A probe step asserts `g++ -std=c++26` yields `__cplusplus == 202400` before the build runs. `actions/checkout` was bumped from `v2` to `v4` and `software-properties-common` added to the dependency install (needed for `add-apt-repository`). Verified end-to-end in a real `ubuntu:24.04` container: the PPA provides `gcc-15 15.2.0-14ubuntu1~24~ppa1`, and the full `make` completes with exit 0, zero compiler diagnostics, and objects stamped `GNU C++26 15.2.0 -std=c++26`.
- Build system: fixed two structural hazards that blocked adding a unit-test harness (see `.squad/decisions/inbox/lead-test-harness-scoping.md` §3).
  - **Source auto-discovery no longer sweeps test files into the game binary.** `Makefiles/default_vars.mk` now excludes any `tests` directory from the `find` that populates `SRCS` (`-not -path '*/tests/*'`). Previously a `src/tests/` directory would have been compiled into `obj/` and linked into `Extermination`, colliding with `src/main.cpp`'s `main()`. The exclusion makes this safe by construction; unit tests should still live in a top-level `tests/` directory outside `src/`.
  - **Added a `main()`-free object seam for future test binaries.** `Makefiles/default_vars.mk` defines `GAME_OBJS_NO_MAIN := $(filter-out obj/main.o,$(OBJS))` so a future test target can link the real game objects alongside a test framework's own `main()` (e.g. `libgtest_main`) without a duplicate-symbol collision. The game build itself does not use this variable.
  - No test files, test targets, or dependencies were added; `make test` is unchanged.
### Changed
- Build system: the top-level `Makefile` now builds the `Yuna` submodule with CMake/Ninja instead of recursing into a Makefile. `Yuna` replaced its Makefile with a CMake build, so `make -C Yuna/.` failed with "No targets specified and no makefile found". The `Yuna.a` target now runs `cmake -S Yuna -B Yuna -G Ninja -DCMAKE_BUILD_TYPE=Debug` followed by `ninja -C Yuna`, matching how `Yuna`'s own CI builds it. The library artifacts moved accordingly: `Yuna/Yuna.a` → `Yuna/libYuna.a` and `Yuna/mfGUI/lib/libMFGUId.a` → `Yuna/lib/libMFGUId.a`, and `LIBDEP` was updated to match.
- Followed the `Yuna::Core::Window::Render` → `Window::Display` rename (the shader overload keeps its signature). Updated the four call sites in `Menu::Render`, `Options::Render`, `Splash::Render`, and `Game::Render`.
### Changed
- Migrated all UI code to the new `mfGUI` component API. The `mfGUI` submodule was updated upstream with a breaking refactor, so `Yuna` and `Extermination` were brought in line with it:
  - **Smart pointers.** Widget handles (`mf::Button`, `mf::List`, `mf::Text`, `mf::Container`, `mf::Slider`, `mf::Image`) are now `std::shared_ptr` instead of raw pointers, in both local variables and class members (`HUD::mNextWaveButton`, `Options::mOptionsContainer`/`mControlsOptionsList`/`mGraphicsOptionsList`/`mAudioOptionsList`/`mMainOptionsList`/`mButtonToBind`, `Yuna::Core::Console`'s widget members). The manual `delete` of the controls list is gone now that it is a `shared_ptr`.
  - **Chain-calling removed.** Setters return `void`, so every chained construction site became a sequence of separate statements. Affected: `Menu::InitMenuItems`, `Options::InitOptionsItems`, `Options::InitControlsOptions`, `Options::InitButtonBinding`, `Options::InitGraphicsOptions`, `Splash::Init`, `HUD::InitNextWaveButton`, and `Yuna::Core::Console::InitUI`.
  - **Component accessors.** Text and background styling moved off the widgets and onto their components: `GetText()->SetString/SetColor/SetPos/LoadFont/SetSize` and `GetBackground()->SetBackground`. `Text::AddText()` was removed in favour of `component::Text::AddString()`, and `Text::SetText()` now takes a `component::Text` rather than a `std::string`. The slider's track and handle are reached via `GetBackground()` and `GetButton()->GetBackground()`.
  - **Helper signature.** `Utils::initBtnHover` now takes a `std::shared_ptr<mf::Button>` and drives the hover effect through the component accessors.
  - `List::ClearWidgets()` no longer takes an argument.
  - Verified with a from-scratch rebuild (`rm -rf obj Yuna/obj && make`): exit 0, zero compiler diagnostics under `-Wall -Werror -Wextra`, and the game still reaches `Game::Init()` at runtime.
### Added
- Next-wave button now has a 30-second auto-launch countdown. The button label shows the remaining seconds (`Next wave (30s)` … `Next wave (1s)`); if the player does not press it, the next wave launches automatically when the countdown reaches zero. Pressing the button manually still launches the wave immediately and restarts the countdown. The timer only runs between waves (while no enemies are alive) and is paused together with the world while the console is open, so it never ticks during an active wave or while the game is paused.
- Three troubleshooting commands for the in-game console (`Tab`), so runtime state can be inspected from the real terminal instead of only through screenshots:
  - `history [count]` — dumps the console's command history to `stdout`, newest first, with a header and footer. The optional `count` argument limits how many entries are printed (clamped to the history size); a non-numeric argument returns `BAD_ARGUMENTS`. This is the command that makes the console useful for headless troubleshooting, since `Console::AddString` only writes to the in-game text box and never echoes to `stdout`.
  - `stats` — prints a one-shot snapshot of live game state to `stdout`: FPS, frame time, entity count, enemy count, next-wave countdown, and the player's position and velocity.
  - `next_wave` — immediately launches the next wave and reports the resulting enemy count. Documented as a debug/cheat command; it is always registered.
  - Supporting change: `Yuna::Core::Console::GetHistory()` was added as a read-only accessor for the private `mHistory` deque (`Yuna/includes/core/console/Console.hpp`). The existing internal `help`, `clear`, and `bind` commands were left untouched.
### Fixed
- Next-wave button countdown text no longer overflows below the button. The label was wrapping onto a second line because the default character size (30) made the string wider than the button, and the text used a fixed top-left offset. The button is now 230px wide with an explicit character size of 20, and the label is recentered inside the button every frame, so the full `Next wave (NNs)` string stays on one line and inside the button for every countdown value from 30s down to 0s.
- Fixed eight bugs found while scoping the unit-test harness:
  - `Inventory::PreviousItem` unsigned underflow and missing bounds check in `GetSelectedItem` — an empty inventory could index out of bounds; `GetSelectedItem` now returns `nullptr` when there is no valid selection, and `NextItem`/`PreviousItem` handle the empty case explicitly. Wrap-around for non-empty inventories is unchanged.
  - `Map::FitToGrid` pushed foliage into `mBlocks` while range-iterating it, invalidating the loop reference on reallocation. Now iterates a snapshot of the original block count; generated foliage is identical.
  - `Map::GenerateGround` pushed ground blocks while indexing `mBlocks`, and read `mBlocks[i + 1]` one past the end on the final iteration. The growing-size iteration is now explicit and documented (it is load-bearing — it fills the ground downward), and the `i + 1` access is bounds-checked. Generated ground is identical.
  - `WaveManager::NextWave` could spin forever when `rand()` kept picking an unaffordable enemy type; it now picks only among affordable types and breaks when none are affordable. `mBuyingPower` growth is clamped to `uint16_t` max instead of silently overflowing. Wave composition is unchanged for the current enemy dictionary.
  - Removed a dead shader load: `World::InitShader` loaded `assets/shaders/global_lighting.frag`, which never existed and was never called or used. The scene darkening is handled by `post-effects.frag` in `Game`.
  - `Weapon::Shoot` leaked every projectile: raw `new` handed to `ProjectileManager`, which removed pointers from its list without deleting them. `ProjectileManager` now owns its projectiles via `std::list<std::unique_ptr<Projectile>>`.
  - Added direct `<cmath>` includes to files using `M_PI` and other math functions, which previously relied on SFML transitively including it.
